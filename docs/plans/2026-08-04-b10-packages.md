# Plan, B10 packages on PyPI and npm

*Stage 4. Written 2026-08-04, against the spec of the same date and issue #3.*

**Gate.** This is a human review gate. No implementation code exists yet.

## Shape

One pull request. Two of the six acceptance criteria cannot be proven before a
tag exists, and they stay unticked through the whole pull request rather than
being ticked on the mechanism that would eventually prove them. B5 ran that way
and the criterion it left empty was the one that turned out to be wrong.

## What this plan refuses to assume

Five, and each has to be measured before anything claims it. B9's plan carried
three refusals, two of them paid, and the one that paid hardest was the one
about a number that had been measured against the wrong thing.

**1. That a publish workflow that reads correctly can publish.** Nothing about
OIDC, trusted publishers or `--provenance` gets claimed until a real tag pushes
a real package and the post-publish job installs it from the registry. B5
assumed jsDelivr treats a tag the way it treats a pinned commit, and that was
wrong, and finding out cost one throwaway tag instead of one wrong sentence in a
README.

**2. That the wheel carries what the source tree carries.** Hatchling selects
files through the VCS ignore rules, which is why `bible.db` is correctly absent
and why something else could be absent for the same reason without anyone
noticing. Verified by importing from `site-packages` with the source tree off
the path and the working directory somewhere else, not by reading the file list.

**3. That the first boot costs 4.9 seconds.** That was measured on this laptop
with a warm page cache. No number reaches the README until a cold CI runner
produces one, and if it is materially worse the design goes back to the author
rather than the number going quietly into a document.

**4. That the version agrees everywhere because one script writes it.**
`openapi.json` gets its version from FastAPI reading `__version__`, not from
`build-artifacts.py`. Two paths, one number, and the test asserts all five
rather than trusting the generator that only owns three.

**5. That npm accepts this package.** 13.3 MB packed, 49 MB unpacked, 371 files.
The registry's size limits could not be established from the documentation, so
the first evidence will be a publish that succeeds or an error that says why.

## Where test-driven development does not apply

Two workflow files and one registry configuration.

`release.yml` cannot be unit tested and neither can the pre-publish install job.
Their verification is that they run, and the pre-publish one runs on every push
from the moment it lands, so it is exercised long before it matters.

**The trusted publisher configuration is not mine to make.** Both registries
need a one-time entry in their web interface naming this repository, this
workflow file and this environment, and neither has an API path this repository
should be using. It is a hand-off to the author, it happens before the first
tag, and the epic does not close until it has happened.

Everything else is ordinary logic and gets tests first.

## Tasks

**1. `LICENSE`, and the metadata pointing at it.** MIT for the code and a data
section naming the per-asset terms with the OpenBible attribution. A test asserts
the file exists, carries the MIT grant, carries the CC BY notice, and that
`pyproject.toml` declares `license-files` rather than a bare SPDX expression the
bundle does not satisfy.

**2. Rename the distribution to `the-catholic-bible`.** `pyproject.toml` only.
The import package does not move and no source file changes. A test pins the
distribution name, because the whole epic fails silently if it drifts back.

**3. Database path resolution.** `CATHOLIC_BIBLE_DB`, then the packaged path when
the file is already there, then a version scoped cache directory. Tests first,
one per branch, plus one asserting the cache path contains the version, which is
the branch that stops `pip install -U` reading a stale database.

**4. The first boot builds, and says so.** `catholic-bible-api` builds when the
resolution finds nothing, prints what it is building and where, and serves. A
test drives it through a temporary directory rather than a real boot.

**5. `catholic-bible-build-db`.** An entry point over
`catholic_bible.storage.build`, which `scripts/build-db.py` already calls. The
script keeps working and gains nothing.

**6. `package.json`, generated.** Into `build-artifacts.py`, which already reads
the version, already writes into the tree and already has the `--check` gate CI
runs. `main` points at `data/index.json`, `files` limits the tarball to `data`,
the README and the licence, no dependencies and no `exports`.

**7. The version agrees in five places.** `pyproject.toml`, `package.json`,
`index.json`, `manifest.json`, `openapi.json`. One test, and it fails on any
disagreement rather than on a chosen pair.

**8. The pre-publish job.** Build the wheel, install into a clean virtualenv,
run the conformance corpus against the installed copy, run the documented
quickstart against the installed entry point, assert the published response.
This is criterion 6 and it runs on every push.

**9. `release.yml`.** On `push: tags: v*`, beside `cdn.yml`. Two jobs, both
`id-token: write`, PyPI trusted publishing and `npm publish --provenance`. Then
the post-publish job that installs from both registries and runs the quickstart,
retried the way `cdn.yml` retries jsDelivr.

**10. The README, through the voice skill.** `pip install` above the fold with
three lines of library before any server. `npm i` beside the CDN line, since it
is the same bytes by a second road. Docker moves under Development. The
Portuguese README moves with it or the two disagree, which is what happened once
already and cost a correction.

**11. `DECISIONS.md`.** The name that was taken, the one distribution against
the epic's two, the implicit first boot against the explicit command, and the
licence that could not be one identifier.

## Order, and why

One to seven before eight, because eight installs what they produce. Eight
before nine, because a publish workflow guarded by nothing publishes whatever
the last commit happened to contain. Ten last, so the README describes what
exists rather than what was planned.

## What closes and what does not

Four criteria close inside the pull request. The parser and canon installable
with `pip`, the dataset installable with `npm`, the version rule documented, and
the conformance corpus running against the installed package.

Two close on the tag. Published from CI rather than a laptop, and the quickstart
using the package, which is only true once the package a stranger installs is
the one the README names.
