# Plan, B3 read API

*Stage 4. Written 2026-08-02, against issue #5 and the spec dated the same day.*

**Gate.** The spec was approved before this was written. Implementation starts
after this document, not before.

Milestones are written against the ten acceptance criteria rather than against a
shape. The B1 plan decomposed nine milestones around a shape and still missed a
criterion, which was found at the acceptance walk with the code already written.
Each milestone below names the criteria it closes and the last one checks that
every criterion was named by somebody.

## The three questions the spec left open

### How 219 authored strings get verified

A conformance case per authored string is the house rule. A second table
transcribed by the same hand on the same afternoon is not a check, it is the same
mistake written twice, so the cases are generated from invariants that hold
against data this repo already has.

**Round trip through the alias table.** Every authored abbreviation has to
resolve through `ALIASES.resolve()` back to its own book code. The alias table is
built from exported Portuguese data, the Douay export and the existing authored
Latin, so it is not the thing being tested. This catches an abbreviation pasted
against the wrong book and it catches a duplicate.

**Subsequence against a name the book actually has.** Every letter of an
abbreviation has to appear in order, ignoring case, a leading numeral and a
trailing period, in at least one of that book's names in that language. It
survives contractions, which a prefix rule would not, and it is mechanical, so
one test covers all 219 without a human rereading a table.

**Against any of its names and not only the canonical one**, which is a
correction made while writing this rather than discovered in code. `Ecclus.` is a
subsequence of `Ecclesiasticus` and `Sir.` is not, because `Ecclesiasticus`
carries no `r`. Both are correct abbreviations for the same book and the modern
name `Sirach` is already in `authored_names.py`, so the rule reads over the whole
name set or it rejects a right answer.

It earns its place on the pair this canon actually confuses. `Ecclus.` against
`Ecclesiastes` fails, because `Ecclesiastes` has no `u`. Sirach and Ecclesiastes
are the two books an English reader mixes up and the check catches exactly that.

**Uniqueness.** No two books share an abbreviation and no authored abbreviation
collides with an existing alias for a different book. `ALIASES.conflicts()`
already reports collisions and a test already pins the two known ones, so a new
collision fails the build rather than quietly losing.

**What none of this catches**, stated plainly rather than left implied. If the
conventional English abbreviation for Sirach is `Sir.` and `Ecclus.` is written
instead, every invariant above passes. All three checks answer "is this string
consistent with this book", and none answers "is this the form the tradition
uses". That question needs a human reading a table against a printed Bible, it
happens once at review, and `LIMITS.md` records that it is the weakest link in
the reference string.

### Connection lifecycle

One read only connection per request, opened `mode=ro` from a module level path.
No pool and no lock.

`sqlite3` connection objects are not thread safe and uvicorn runs sync handlers
in a threadpool, so a module level connection is the answer that passes every
test and fails under concurrency. A pool is the other answer and it is not earned
yet, because opening a read only SQLite connection against a warm page cache is
microseconds and this service has no users.

Verified rather than assumed. A test drives the API from several threads at once
and QA measures the open cost against a real request, so the number that would
justify a pool exists before anyone argues for one.

### How the tests get a database

A session fixture builds the real database once into a gitignored path and reuses
it if it is already there and newer than its inputs. Seconds once per machine
rather than seconds per red green cycle.

Storage unit tests use a small in memory database built by the same builder
function, so the schema under test is the schema that ships. A hand written test
schema drifts from the real one and the drift shows up in production.

## Milestones

### M1. The store

Criterion 10, and the seam every later milestone reads through.

- `scripts/build-db.py`, reading the committed corpus JSON, `canon.json` and
  `versification.json`, writing tables for the canon, the spine and the verse
  texts, indexed on the dense canonical order
- `db` target in the `Makefile`
- `*.db` in `.gitignore` and in `.dockerignore`, so a laptop built database
  cannot be committed and cannot be copied into the image
- a build step in the `Dockerfile` before the application layer
- a step in the CI `checks` job, which is a bare `pytest` today and would go red
  the day this merges
- `src/catholic_bible/storage/`, the read side, which is empty today while
  `README.md` already advertises what it holds

Tests. Row counts match the published files, 107103 verses, 35845 spine
addresses, 73 books. A range query by canonical order returns contiguous verses
across a chapter boundary. The schema leaves room for an FTS5 table beside it,
asserted by building one in a test and not by a comment claiming it.

### M2. The authored strings

Feeds M3 and nothing else can start without it.

- 73 English abbreviations, 73 Latin abbreviations, 73 Douay names in ordinary
  case, in `authored_names.py` beside the Latin names, in code rather than JSON
- the three invariants above, as tests over all 219

The Douay names are the delicate set. `1 KINGS` is Samuel in that reckoning and
`3 KINGS` is what most editions call 1 Kings, and title casing produces
`Canticle Of Canticles`.

### M3. The formatted reference

- port `BibleReferenceFormatter`, keeping its language parameter, which the
  original has and has never had data behind
- comma between chapter and verse in Portuguese and Latin, colon in English
- single verse, same chapter range, cross chapter range, disjoint parts with the
  chapter reprinted only when it changes, whole chapter

Tests are the ported cases in three languages. `Eclo 24,1`, `Ecclus. 24:1`,
`Eccli. 24,1`.

### M4. The error model, and the canon listing

Criteria 1, 4, 5 and 9, opened here because every route needs the error shape
before it can document one.

- the API reason enum, nine members, four of them new
- `UnparsedReference.reason` becomes a `StrEnum`, which the spec found is a bare
  `str` with nothing closing it
- `GET /v1/versions` and `GET /v1/versions/{version}/books`, in the version's
  language, with `default` on `matos-soares`
- the short revalidating cache header on both, not the immutable one

Tests. An unknown version is a 404 carrying `unknown_version`. Every book of a
version lists in canonical order. Names come back in the version's language, so
Douay returns `Josue` and the Vulgate returns `Iosue`.

### M5. Reading a chapter and a verse

Criteria 1 and 4.

- the book, the chapter and the single verse routes
- `previous` and `next`, crossing book boundaries, skipping books the version
  does not cover, `null` at the two ends of the canon
- `numbering` on chapter responses, from the ported table
- the immutable cache header, here and not on M4's routes

Tests. Genesis 1 has no previous. Revelation 22 has no next. A chapter whose
neighbour is the last chapter of the previous book points at that book.
`PSA.150.6` is a 404 in Douay carrying `unpublished_in_version` and a 200 in the
other two, which is the distinction the whole taxonomy exists for. Psalm 9
carries `9-10` and Psalm 3 carries `3`.

### M6. Resolving a reference

Criteria 2 and 9.

- `GET /v1/resolve`, with `scheme` defaulting to `spine`
- an address mapped through `map_address` before anything is read, and an orphan
  returned as a 422 naming its reason
- `preview`, the first verse of the span in the default version
- whole chapter and multi chapter references refused with `whole_chapter`

Tests. `Jo 3,16` and `Jó 3,16` land in different books, which is criterion 2 and
the reason the repo exists. `Sl 51,1` with `scheme=org` lands on `PSA.50.1` and
without it lands on `PSA.51.1`, and both are correct answers to different
questions. `Ex 13-14` is a 422 rather than a 200 returning half of Exodus 13.

### M7. Passages and ranges

Criteria 1 and 3.

- `GET /v1/passage`, 1 to N versions aligned by verse id
- an explicit null where a version does not carry a verse, never a shortened
  column
- disjoint parts unioned in canonical order without duplicating an overlap
- the cap as a span on the dense order rather than a count, which is the ported
  behaviour

Tests. A range crossing a chapter boundary, which is criterion 3. A range
crossing a book boundary. Two versions where one has a gap, asserting the null
sits in the right column. A contiguous 501 verse range passes and a two verse
disjoint reference 600 orders apart is refused, both of which are the ported
semantics rather than an accident.

### M8. Read only, proved twice

Criterion 8.

- a test walking every route and failing anything that is not a `GET`
- the connection opened `mode=ro`, so a write raises at the driver rather than
  being caught by a convention

Two independent proofs because a convention holds until somebody adds a route in
a hurry.

### M9. The document gate

Criteria 5, 6 and 7.

- `scripts/build-openapi.py`, `openapi.json` committed at the root
- a CI step regenerating and diffing, which catches a route that changed without
  the document following
- a test walking the routes and failing any that carries no summary, no response
  model or no documented error responses

The second direction is the one that rots quietly. FastAPI publishes an
undocumented route without complaining and nothing else notices.

### M10. Thirty conformance cases through HTTP

Criteria 2 and 3, verified the way the epic asks rather than the way that is
convenient.

All 30 cases run through `resolve`, the 15 `map` ones with `scheme` set. Thirty
cases passing as unit tests say nothing about what survives a URL encoder, and
`Jó 3,16` arriving as `J%C3%B3%203,16` is exactly where an accent gets folded.

A test pins the two psalm disagreements between the ported table and `to_scheme`,
so the day the B1 defect is fixed the suite says which one moved.

### M11. The criteria walk, and the documents

- every criterion walked one by one with its evidence, unmet ones left unchecked
- `README.md` quickstart gains a real reading call, and the CI quickstart job
  runs it, so the five minute claim is executed rather than written
- `README.md` stops advertising FTS5, which arrives in B9
- `DECISIONS.md` gains the calls with a loser: no envelope, path prefix
  versioning, SQLite over reading JSON with the measured 34.8 MB, the reason enum
  with RFC 9457 as what lost, the reference string shipping while `display_label`
  does not
- `LIMITS.md` gains the weakest link in the reference string, which is that no
  check in this repo knows whether an authored abbreviation is the form the
  tradition uses
- the B1 defect gets an issue of its own, with the two addresses and the repro

## Where test driven does not apply

Named rather than faked with a test that asserts a file exists.

**The Dockerfile and the CI steps.** Verified by running `docker compose up` on a
clean checkout with no credentials and reading Sirach 24:1 out of it, recorded in
the QA notes.

**`openapi.json` itself.** It is generated, so a test asserting its content would
be a test of FastAPI. What is tested is the two gates around it, the diff and the
route completeness walk.

**The 219 authored strings, at the level that matters.** The three invariants are
tested. Whether each is the form the tradition prints is a human reading a table,
once, at review.

## Risks

**The authored strings are the largest unreviewed surface this repo has had.**
219 hand written values, and the checks catch consistency rather than
correctness. The mitigation is that they are in code where a reviewer reads them
as decisions, and that `LIMITS.md` says what was not verified.

**`previous` and `next` are more logic than they look.** Crossing a book
boundary while skipping books a version does not cover is where an off by one
lives, and the 432 unfilled addresses mean a version can be missing verses in a
chapter it does cover, which is not the same thing as not covering the book.

**The scheme parameter widens the public surface on day one.** Four values, and
three of them go through B1 code carrying a known defect. The two known wrong
answers are pinned, and whether more exist in the other 72 books is not
measurable here.

**Memory under uvicorn was measured for the JSON path and not for SQLite.** The
comparison that justified SQLite used 34.8 MB retained for the alternative. The
SQLite side has a page cache per connection and a connection per request, and
that number does not exist yet. QA measures it, and if it is worse the decision
gets revisited in writing rather than defended.
