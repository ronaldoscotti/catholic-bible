# Spec, B10 packages on PyPI and npm

*Stage 3. Written 2026-08-04, against issue #3.*

**Gate.** This is a human review gate. Two design questions were asked before
this document was written. The package name came back as `the-catholic-bible` on
both registries, and the shape came back as one Python distribution carrying
everything. Both answers are folded in.

**One of those two answers rested on a premise this document had to withdraw.**
The recommendation that won said `pip install` would leave the API running. It
does not, and the section that says so is the reason three more questions went
to the bottom. Those three came back the same day. The licence is MIT and the
other two were handed back with a rule rather than an answer, so the section
that closes this document carries the reasoning as well as the decision.

## What B10 delivers

Installing this the way everything else gets installed.

Today the only way in is a clone, and the epic is right that a clone loses most
of the people who would otherwise have used it. A download count is also the
only public, falsifiable evidence that any of this made somebody's work easier,
and this repository has none.

### The name check came back against us

The epic carries a constraint that names get checked and claimed before this
starts. The check ran and `catholic-bible` on PyPI belongs to somebody else, has
since March, and is an unrelated scraper of `bible.usccb.org`.

`pyproject.toml` declares that name today. Nothing was ever published from here,
so nothing broke, and what it means is that the name in the build metadata could
never have worked. Had B10 started by writing a publish workflow, the first tag
would have failed on an authorisation error against a stranger's project.

### The premise that failed

The recommendation for one distribution rested on `pip install` giving a working
API in one command, which reads better than a clone and a Docker daemon. Built
the wheel, installed it into a clean virtualenv, ran the entry point.

```
$ ./probe/bin/catholic-bible-api
$ curl -i http://localhost:8000/health
HTTP/1.1 503 Service Unavailable

{"detail":{"reason":"store_unavailable","message":"no database at
/.../site-packages/catholic_bible/data/derived/bible.db. run `make db` to build
it","input":null}}

$ curl http://localhost:8000/v1/versions
Internal Server Error
```

`bible.db` is derived, so it is gitignored, so hatchling leaves it out of the
wheel. Every `/v1` route answers 500 and `/health` answers 503. The message
tells the reader to run `make db`, which is a Makefile target in a repository
they do not have, so the one instruction the failure offers is unreachable from
where they are standing.

That is not an argument against the answer that was given. It is one piece the
answer needs and did not have, and it is the first decision below.

## Decisions

### The distribution is renamed and the import is not

`the-catholic-bible` on PyPI and `the-catholic-bible` on npm. `catholic_bible`
stays the import, unchanged, so no source file moves.

One name across both registries because a reader who finds one has to be able to
guess the other. A distribution whose install name differs from its import name
is ordinary on PyPI and still surprises people, so the README says both on the
line where it says either.

**What lost.** `catholicbible`, `catholic-canon` and `deuterocanon` were all
free. The first is the same name with the hyphen taken out, which is how
typosquats are read and how support questions land in the wrong project's
tracker. The other two describe a part of this and would have to be explained
every time.

### One Python distribution, carrying everything

The author's answer. `the-catholic-bible` ships the parser, the canon, the
spine, all three translations, the commentary, the cross-references and the API.

This diverges from the epic's framing, which describes two packages with two
jobs and puts data on npm and code on PyPI. Under that split the Python wheel
would be 84 KB and `pip install` would stop giving anyone a running service. The
cost of the answer chosen is 13 MB for a reader who only wanted to parse
`Eclo 24,1`, and it buys a reader who wanted the whole thing an install instead
of a checkout. `DECISIONS.md` records the divergence and this reasoning.

### The database is built on first boot, into a directory the process can write

`catholic-bible-api` builds `bible.db` when it is missing, says so on stdout,
and takes 4.9 seconds once. Nothing else changes about how it runs.

Where it writes resolves in three steps, first hit wins.

1. `CATHOLIC_BIBLE_DB`, if set. This is the operator's override and it is also
   what the tests use.
2. The packaged path, `catholic_bible/data/derived/bible.db`, when the file is
   already there. This is the repository and the Docker image, both of which
   build it ahead of time, and neither changes behaviour.
3. A per-user cache directory. This is the installed case, and it is the only
   new path.

The third step exists because `site-packages` is not reliably writable. A system
install, a container with a read-only filesystem and a wheel installed as root
then run as an unprivileged user all fail to write there, and a first boot that
crashes on permissions is worse than the 503 it replaces.

**What lost.** Shipping `bible.db` inside the wheel costs 29 MB and publishes a
derived artifact carrying no checksum and no provenance record, which every
other published file in this repository carries. Requiring a second command
before the first one works is honest and turns the quickstart back into two
steps, which is most of what the clone cost.

### The npm package is `data/` and nothing else

The 371 artifacts B5 already generates, published unchanged. No dependencies, no
JavaScript, no parser, which the epic's constraints require and which this
document is not reopening.

`main` points at `data/index.json`, so `require('the-catholic-bible')` returns
the file that lists what exists and how the URLs are shaped. That file already
answers the entry point question for CDN readers and it answers the same one
here.

No `exports` field, so every path under `data/` is reachable by name. A data
package that restricts subpath access is restricting the only thing it does.

### `package.json` is generated, and the version has one source

`pyproject.toml` holds the version. It already reaches `index.json` and
`manifest.json` through `build-artifacts.py`, and `openapi.json` through
FastAPI. B10 adds `package.json` to the same generator rather than a second one,
because that script already reads the version, already writes into the tree and
already has the `--check` gate CI runs.

A test asserts all five agree. Five files carrying one number by convention is
the arrangement where one of them goes stale and nothing notices, which is what
`LIMITS.md` was doing to the orphan rate for two epics.

No hand-edited `package.json`. The rule that no JSON is authored here does not
have an exception for build metadata.

### Publishing runs on a tag, over OIDC, with no stored token

A `release.yml` beside `cdn.yml`, on `push: tags: v*`, two jobs.

PyPI Trusted Publishing and npm Trusted Publishing, both by OIDC with
`id-token: write`. Neither registry needs a long-lived secret in this
repository, and `npm publish --provenance` signs the package against the
workflow and commit that produced it.

Both require a one-time configuration in the registry's web interface, naming
this repository and this workflow. Neither can be done from here. That hand-off
is in the open questions.

### The conformance corpus runs against the installed package

Criterion 6. The wheel is built, installed into a clean virtualenv, and
`tests/canon/test_conformance.py` runs with the source tree off the path.

Running it against `src/` proves nothing about a package. B7 has the shape of
the failure this guards against, where `py.typed` was checked into the tree and
the question of whether it reached the wheel was a different question that
`tests/test_packaging.py` had to ask separately.

## Boundaries

No JavaScript parser and no second Python distribution.

The CDN is untouched. jsDelivr keeps serving the same files from the same tags,
and npm is an additional way to the same bytes rather than a replacement.

Nothing here deploys anything. The API still runs nowhere public and B6 owns
that.

The `catholic-bible` name on PyPI is not contested, not requested from its
owner, and not worked around. It is somebody's project.

## Verification

Two layers, because a package that builds is not a package that installs.

**Before publishing**, in CI on every push. Build the wheel, install it into a
clean virtualenv, run the conformance corpus against the installed copy, run the
documented quickstart against the installed entry point and assert the response
the README publishes.

**After publishing**, on the tag. Install `the-catholic-bible` from PyPI and
`the-catholic-bible` from npm into empty directories and run the same documented
quickstart against what the registries actually serve. Retried, the way
`cdn.yml` retries jsDelivr, because a registry that has accepted a publish has
not necessarily finished propagating it.

The second layer is the one the epic asks for and the one that can fail for
reasons the first cannot see.

## The three questions, answered 2026-08-04

The author answered the first and handed the other two back with a rule, which
is to take the industry standard and the better experience for the reader. What
follows is the reasoning that produced each answer, so the answer can be argued
with rather than only obeyed.

### The licence is MIT, and it does not cover the corpus

The author's answer, and it settles the half that had no answer at all. The code
here had no stated terms, so a reader could read the parser and could not
legally reuse it.

**A single MIT declaration on either package would be false.** The wheel and the
npm tarball both carry the corpus, and `LIMITS.md` audits it asset by asset.
Matos Soares is public domain under Brazilian law, the Douay margins are CC0,
and the OpenBible cross-references are CC BY 4.0 with attribution required. MIT
over that bundle relicenses somebody else's work and drops an obligation this
repository has honoured everywhere else, including inside every published file.

So `LICENSE` at the root carries both halves. The MIT text governs the code. A
second section states the data terms per asset, repeats the OpenBible notice and
points at `LIMITS.md` for the full audit. Both packages point at that one file
rather than each restating it, `package.json` with `SEE LICENSE IN LICENSE`,
which is npm's own form for a bundle no single identifier describes.

`pyproject.toml` declares `license-files` and no bare SPDX expression, for the
same reason. A field that can hold only `MIT` should hold nothing when `MIT` is
not the whole truth.

### The README leads with the package and keeps the container

**Industry standard is the install command first and a container further down.**
A reader arriving at a Python project expects `pip install` above the fold and
expects Docker under development or deployment. This README has it backwards
today, where the only thing called Quickstart is a clone plus a Docker daemon.

**The better experience comes from noticing this README serves three readers.**
One wants the data and nothing else, one wants to parse a reference in Python,
one wants the HTTP API. The CDN section already answers the first and stays
exactly where it is, first, because for most people it remains the right answer.
Quickstart answers the other two, in that order, with `pip install` and three
lines of library before any server appears. `npm i` joins the CDN section, since
it is the same bytes by a second road.

**Docker stays in the README and moves under Development**, beside `make run`,
which already describes it. Criterion 5 asks that the quickstart use the package
rather than a clone. It does not ask that `compose.yaml` stop being the contract,
and `CLAUDE.md` says it is one.

**CI gains a job and loses none.** The compose quickstart keeps running exactly
as it does now, and a second job runs the pip path against the same published
responses. A path demoted in the README is not a path that stopped being
promised.

### The database builds on first boot, and the cache is version scoped

**The standard splits on whether materialising the data needs the network.**
Playwright and spaCy make it an explicit command because the alternative is a
surprise download of hundreds of megabytes. Transformers and `tldextract` do it
implicitly on first use because the work is local and cached.

This work is local, needs no network, and takes 4.9 seconds to rearrange bytes
the reader already downloaded when they installed the package. That is the
implicit case. Asking for a second command to convert a file into a different
file that was already on disk is the papercut both of those explicit tools are
famous for, and neither one chose it for this reason.

It prints one line naming what it is building and where, because four seconds of
silence on first boot reads as a hang.

**The cache path carries the version.** `<cache>/the-catholic-bible/<version>/bible.db`,
not a single path reused across upgrades. `LIMITS.md` already has a heading
called *A stale database ships without a sound*, saying that nothing readable
from inside a database says when it was filled. A cache keyed on nothing would
hand that exact failure to every reader who ever runs `pip install -U`, and this
is the one place in the design where doing the simple thing would reintroduce a
limit this repository has already written down.

**`catholic-bible-build-db` ships as well**, for the one caller that genuinely
wants it explicit. An image built `FROM python` with a `pip install` layer wants
the database in a layer rather than rebuilt on every container start.
`scripts/build-db.py` already delegates to `catholic_bible.storage.build`, so
this is an entry point rather than a second implementation.
