# Spec, B3 read API

*Stage 3. Written 2026-08-02, against issue #5. Second draft, after review.*

**Gate.** This is a human review gate. Nothing here has been approved and no
code has been written.

The first draft was reviewed and did not survive it. Four of its numbers were
wrong, it dropped four ported behaviours without naming them, and its headline
field could not represent the data it was designed to carry. What changed is
recorded at the end, under [What the first draft got wrong](#what-the-first-draft-got-wrong),
rather than quietly rewritten.

## What B3 delivers

Scripture over HTTP, answered by reference. Seven routes, a published OpenAPI
document, and the gate that keeps that document honest.

It is the first public seam this repo has. B1 and B2 could be corrected by a
commit. A route that ships wrong has consumers.

bulk is ordinary coverage, 86 addresses in Proverbs and 73 in Sirach that Matos
Soares does not carry.

## The routes

```
GET /health                                                   unversioned
GET /v1/versions
GET /v1/versions/{version}/books
GET /v1/versions/{version}/books/{book}
GET /v1/versions/{version}/books/{book}/chapters/{chapter}
GET /v1/versions/{version}/books/{book}/chapters/{chapter}/verses/{verse}
GET /v1/passage?ref=&versions=&scheme=
GET /v1/resolve?ref=&scheme=
```

**Versioning is a path prefix.** Header and media type versioning both lose,
because B5 publishes static artifacts a browser fetches by URL and a one line
`fetch()` cannot negotiate a media type. The version has to be in the address.

**Reading routes are nested nouns rather than the flat shape they replace.** The
private repo serves `/{version}/{book}/{chapter}` and orders its literal
prefixes ahead of it deliberately, with route constraints on top. That works and
it is careful. Nesting is better because it is self describing and because the
care is not needed, not because the original was careless.

`/health` stays at the root and outside `/v1`. It is operational, the CI
quickstart already asserts against it, and it is not part of the contract a
consumer pins.

## Which numbering an incoming reference is written in

This is the front door and the first draft had nothing on it.

`Sl 51,1` parses today, lands on the spine, and returns the spine's Psalm 51,
which is `org` Psalm 52. The reader typed the Miserere and got the wrong psalm,
with a 200 and nothing anywhere saying so. The roadmap opens by naming this
exact failure as the reason the repo exists.

So `passage` and `resolve` take `scheme`, one of `spine`, `vulgate`, `org`,
`douay`, defaulting to `spine`. The address is mapped through B1's `map_address`
before anything is read, and an address that orphans comes back as a 422 naming
the orphan reason rather than as the nearest plausible verse.

This also closes a gap in the verification. The conformance corpus has 15 `map`
cases and without a scheme parameter there is no HTTP surface to run them
through. With it, all 30 run.

## The Psalms carry both numbers, and the counterpart is a string

The Miserere is Psalm 50 on this spine and Psalm 51 in most editions. A reader
who does not see both numbers thinks the API is broken.

The first draft proposed `{"spine": 22, "org": 23}`, an integer pair. It cannot
represent the psalter. Measured verse by verse:

```
spine PSA   9 -> org   9 (vv 1-21) and org  10 (vv 22-39)     one psalm splits in two
spine PSA 113 -> org 114 (vv 1-8)  and org 115 (vv 9-26)      the same
spine PSA 114 -> org 116 (vv 1-9)     two psalms merge into one
spine PSA 115 -> org 116 (vv 10-19)   and 9 verses orphan
spine PSA 146 -> org 147 (vv 1-11)    the same merge
spine PSA 147 -> org 147 (vv 12-20)   and 11 verses orphan
```

`{"spine": 9, "org": 9}` is a wrong answer with nothing to tell the reader.
`{"spine": 115, "org": 116}` implies a correspondence holding for 10 verses of
19.

The private repo already answers this and returns a string, because the answer
is sometimes a range. That table ports as it stands.

```json
"numbering": {"scheme": "org", "counterpart": "9-10"}
```

Twelve psalms carry a counterpart equal to their own number, 1 through 8 and 147
through 150, and those are the ones a client can safely print alone.

**Two disagreements, surfaced rather than averaged.** The ported table and B1's
`to_scheme` agree on 148 psalms and disagree on 2.

| Psalm | Ported table | `to_scheme` |
|---|---|---|
| 15 | 16 | 15-16 |
| 43 | 44 | 43-44 |

Both are the last verse of the psalm and the cause is the same. `org PSA 16:10`
and `16:11` both land on spine `PSA.15.10`, so spine `PSA.15.11` is a Vulgate
tail with no `org` origin. Read back, it returns `org 15:11`, which is a
different psalm, and the round trip check passes because that book maps by
identity and identity always round trips.

**This is a B1 defect and it is not B3's to fix quietly.** `to_scheme` can tell
that a candidate does not return to where it started. It cannot tell that a
candidate is out of range in the target scheme, because this repo holds no `org`
verse count table, only the Copenhagen remap pairs. The honest answer for
`PSA.15.11` in `org` is an orphan and the current answer is a wrong verse
someone could trust, which is the exact class of failure `DECISIONS.md` says B1
exists to prevent.

Two addresses are confirmed. Whether more exist across the other 72 books is not
measurable with what is in this repo, and saying that is better than publishing
a number I cannot stand behind. It needs its own fix, on its own branch, against
B1. B3 ships the ported table, which is hand verified domain knowledge, and a
test pinning the two known disagreements so the day B1 is fixed the test says so.

Verse level dual numbering stays out of the payload. A caller who needs it asks
`resolve` with `scheme=org`.

## The formatted reference

Every private response carries a display ready `reference`. It ships here too,
because it is what a reader sees and rebuilding it in every client is the work
this API exists to remove.

It is formatted in the language of the version being read, never in one fixed
language. The private formatter already takes a language parameter and has only
ever had `pt-BR` data behind it, so the multilingual door is open and nothing
walked through it.

```
pt   Eclo 24,1     Jo 3,16      1Cor 13,4-7    Mc 5,22-24.35-43
en   Ecclus. 24:1  John 3:16    1 Cor. 13:4-7  Mark 5:22-24, 35-43
la   Eccli. 24,1   Ioan. 3,16   I Cor. 13,4-7  Marc. 5,22-24.35-43
```

Portuguese and Latin separate chapter from verse with a comma and English with a
colon. Cross chapter ranges, disjoint parts and whole chapters follow the ported
formatter, which reprints the chapter only when it changes.

### Three sets of authored strings

The names exist. The abbreviations mostly do not.

Portuguese has a name and an abbreviation per book in `canon.json`. English has
Douay names in `douay-names.json` and modern names in `authored_names.py`. Latin
has names in `authored_names.py`. The source database holds 73 name rows in one
language, `pt-BR`, so there is nothing further to export.

So B3 authors three sets, in `authored_names.py` beside the Latin names, in code
rather than JSON, so a reviewer reads them as decisions rather than as data a
script produced.

| Set | Count | Why it does not exist already |
|---|---|---|
| English abbreviations | 73 | never in the source, one language only |
| Latin abbreviations | 73 | the same |
| Douay names in ordinary case | 73 | `douay-names.json` holds the uppercase margin forms |

The third is not mechanical. Title casing produces `Canticle Of Canticles`, and
the Douay reckoning of Kings has to survive, where `1 KINGS` is Samuel and
`3 KINGS` is what most editions call 1 Kings.

Nothing enters without a case in the conformance corpus, including an alias, and
219 authored strings are 219 chances to be wrong. The plan has to answer how
they are checked rather than assert they were.

## The response shape

No envelope. Every route returns its typed model directly, which is what FastAPI
generates a clean document from and what a Pydantic consumer reads without
unwrapping. The `data` wrapper in the private repo is a Laravel convention and it
would put one polymorphic generic over the whole document.

**The verse id is the published string and never the internal integer.** The
private repo answers `"verse_id": 30489`. That integer is an artifact of the
order a seed ran in, B1 decided it stays internal, and a public contract that
freezes it cannot be undone. Any consumer migrating from the private API breaks
on this field, which is the correct trade made once and written down rather than
discovered later.

### `GET /v1/versions`

```json
[
  {"code": "matos-soares", "name": "Bíblia Sagrada", "abbreviation": "MS",
   "language": "pt-BR", "year": 1956, "default": true,
   "rights": {"text": "public-domain", "basis": "…"}}
]
```

`default` is `matos-soares`. The private repo carries the same flag and a reader
opening the app needs something chosen for it.

### `GET /v1/versions/{version}/books`

Books this version reaches, in canonical order, not the raw 73.

```json
[
  {"code": "GEN", "name": "Gênesis", "abbreviation": "Gn",
   "testament": "OLD", "group": "PENTATEUCH", "deuterocanonical": false,
   "chapters": 50}
]
```

`name` and `abbreviation` are in the version's language. `group` is the enum
already in `books.py` and the human label is the client's to render, for the
same reason `display_label` is refused.

### `GET /v1/versions/{version}/books/{book}`

The whole book, single version, grouped by chapter. It ignores `versions`.

```json
{"version": "matos-soares",
 "book": {"code": "JHN", "name": "João", "abbreviation": "Jo", "chapters": 21},
 "chapters": [{"chapter": 1, "numbering": null, "verses": ["…"]}]}
```

Psalms is 2461 verses in one response. That is the reason B5 exists, and it is
still a route the epic asks for.

### `GET /v1/versions/{version}/books/{book}/chapters/{chapter}`

The reader's main route.

```json
{"version": "matos-soares",
 "book": {"code": "PSA", "name": "Salmos", "abbreviation": "Sl", "chapters": 150},
 "chapter": 50,
 "numbering": {"scheme": "org", "counterpart": "51"},
 "previous": {"book": "PSA", "chapter": 49},
 "next": {"book": "PSA", "chapter": 51},
 "verses": [
   {"id": "PSA.50.3", "chapter": 50, "verse": 3,
    "reference": "Sl 50,3",
    "text": "Tem piedade de mim, ó Deus, segundo a tua misericórdia…"}
 ]}
```

`previous` and `next` cross book boundaries and skip books the version does not
cover, and they are `null` at the two ends of the canon. They ship rather than
being dropped, because working out that a version's Genesis 1 has no previous
chapter is canon order logic, and pushing it into every client is the work this
API exists to remove.

### `GET /v1/versions/{version}/books/{book}/chapters/{chapter}/verses/{verse}`

One verse, the same shape as the members of `verses` above.

### `GET /v1/passage?ref=&versions=&scheme=`

1 to N versions aligned by verse id, with an explicit null where a version does
not carry a verse.

```json
{"reference": "Jo 3,16-17", "book": "JHN", "versions": ["matos-soares", "douay-rheims"],
 "verses": [
   {"id": "JHN.3.16", "chapter": 3, "verse": 16, "reference": "Jo 3,16",
    "texts": [{"version": "matos-soares", "text": "Com efeito…"},
              {"version": "douay-rheims", "text": "For God so loved…"}]}
 ]}
```

Never a shortened column. A consumer rendering two translations side by side
gets silently misaligned text and there is no error anywhere. The 432 unfilled
addresses make this concrete rather than theoretical.

`versions` defaults to the default version when absent. The private repo defaults
to an empty list and returns empty text columns, which is a silent empty response
on a public contract.

Which language `reference` is formatted in follows the first requested version.

### `GET /v1/resolve?ref=&scheme=`

The cheap one. A command palette calls it on every keystroke.

```json
{"reference": "1Cor 13,4-7", "book": "1CO",
 "ids": ["1CO.13.4", "1CO.13.5", "1CO.13.6", "1CO.13.7"],
 "preview": "A caridade é paciente, a caridade é bondosa…"}
```

`preview` is the first verse of the resolved span in the default version. It is
what makes `resolve` worth calling instead of `passage`, and it is one lookup.

## Whole chapter and multi chapter references

`Ex 13-14` parses today as chapter 13 anchored, with chapter 14 dropped, and
`Sl 23` parses as a whole chapter. Through `passage` both would be a 200
returning less than was asked for, silently.

Both return 422 on `passage` and `resolve`, which is parity with the private API,
with `reason` naming which shape was refused. A whole chapter has a route of its
own and that is where a caller is pointed.

## Errors

FastAPI emits `{"detail": …}` for its own validation failures and there is no way
to suppress that without fighting the framework. Errors use that key, with a
typed body inside rather than a sentence, so one shape covers the whole document.

```json
{"detail": {"reason": "unpublished_in_version",
            "message": "douay-rheims does not publish PSA.150.6",
            "input": "PSA.150.6"}}
```

The first draft claimed the reason codes were a closed set that already existed.
They are not. `OrphanReason` has five members and `UnparsedReference.reason` is a
bare `str` with no enum behind it. B3 defines the API reason enum explicitly and
turns `UnparsedReference.reason` into a `StrEnum` in the same pass.

| Status | `reason` | When | Exists in B1 |
|---|---|---|---|
| 404 | `unknown_version` | no such version code | no, new |
| 404 | `unknown_book` | no such book in the path | yes |
| 404 | `not_on_spine` | the spine has no such chapter or verse | no, new |
| 404 | `unpublished_in_version` | the spine holds it, this version does not | no, new |
| 422 | `malformed` | `ref` is not shaped like a reference | yes |
| 422 | `unknown_book` | `ref` names no book | yes |
| 422 | `whole_chapter` | `ref` is a chapter, not a passage | no, new |
| 422 | `range_too_large` | the span exceeds the cap | no, new |
| 422 | the five `OrphanReason` values | `ref` orphans under `scheme` | yes |

`unknown_book` carrying 404 on a path segment and 422 on a query parameter is
deliberate. A path names a resource and a query carries user input.

The 404 split is the one that matters. `PSA.150.6` is a real address, Matos
Soares and the Vulgate both carry it, and the Douay fixture has it empty
upstream. A caller has to tell "this verse does not exist" from "this translation
does not have it", because the second has an answer and the first does not.

Messages are English. Reason codes are the contract and the message is the
courtesy.

**RFC 9457 problem details lost.** It is the broader standard and it would mean
either overriding FastAPI's built in validation error shape or shipping two error
shapes in one document. Neither is worth the conformance.

## Ranges

The cap is ported as it stands, and it is a span rather than a count. The private
implementation compares the dense order of the last verse against the first and
refuses above 500. Two consequences follow and both are the ported behaviour: a
contiguous 501 verse range passes, and a two verse disjoint reference whose parts
sit 600 orders apart is refused.

Disjoint references parse today, `Mc 5,22-24.35-43`. `passage` reads every part
and unions them in canonical order without duplicating an overlap.

## Storage is SQLite

The corpus ships as JSON, which is the published artifact and what B5 puts on a
CDN. The API reads SQLite.

**This was argued against in review and it stands.** Reading the JSON costs 34.8
MB retained and one line, and the store would then change underneath routes that
already shipped, on the epic where search arrives. The seam is cheaper to place
before there are consumers than after. `src/catholic_bible/storage/` is already
there and empty, and `README.md` already advertises what it will hold, which
under the honesty rules is a debt this epic pays rather than inherits.

What B3 has to build, none of which exists today:

- `scripts/build-db.py`, reading the committed JSON, the canon and the spine
- a `db` target in the `Makefile`, which the first draft described as if it were already there
- `*.db` in `.gitignore` and in `.dockerignore`, so a laptop built database cannot be committed and cannot be copied into the image
- a build step in the `Dockerfile` before the application layer
- a step in the CI `checks` job, which today is a bare `pytest` and would go red the day this merges

The schema holds the canon, the spine and the verse texts, indexed on the dense
canonical order so a range is one query with a `BETWEEN`. It is laid out so B9
adds an FTS5 virtual table beside it without migrating anything.

The database is derived, reproducible from committed inputs, and not committed.
**It carries no checksum of its own.** The first draft asked whether the file is
byte identical across builds and that was the wrong question. The inputs are
committed and CI already verifies their hashes, so a hash of a file derived from
them proves nothing the input hashes do not already prove.

## Caching

`Cache-Control: public, max-age=31536000, immutable` on the routes that return
verse text. The text of a published version never changes and corrections ship
as a new version, which is already the release policy.

Not on `/v1/versions` and `/v1/versions/{version}/books`. That list grows with
every translation and every epic that adds one, and a client that cached it
immutably for a year never sees the fourth version. Those get a short revalidating
max age.

## The document gate

`openapi.json` is committed at the repository root. A committed script
regenerates it and CI fails when the committed copy differs, which catches a
route that changed without the document following.

The other direction is the one that rots quietly. A test walks the application's
routes and fails any route carrying no summary, no response model, or no
documented error responses. FastAPI publishes an undocumented route without
complaining, so nothing else notices.

The idea is borrowed from the private repo, where a coverage test compares the
client collection against the real routes in both directions and blocks the push
when either side is missing. That mechanism is why the collection there is still
accurate.

## Verification

TDD on the handlers, the resolver, the formatter and the store.

**All 30 conformance cases run through HTTP**, which the scheme parameter is what
makes possible. The 15 alias and reference cases go through `resolve` and the 15
`map` cases go through `resolve` with `scheme` set. Thirty cases passing as unit
tests say nothing about what survives a URL encoder, and `Jó 3,16` arriving as
`J%C3%B3%203,16` is exactly where an accent gets folded by accident. That case is
the reason the repo exists.

The two psalm disagreements are pinned by a test naming both, so the day B1 is
corrected the suite says which one moved.

The 219 authored strings need a check that is not a second copy of the table.

The quickstart job in CI already runs `docker compose up` and asserts the README
response. It gains a real reading call, so the claim that a stranger can read
Scripture in five minutes is executed on every push rather than written down.

## Out of scope

No search, that is B9. No rate limiting, that is B8. No commentary and no cross
references, those are B4. No authentication and no writes, those are refused
rather than deferred.

No multi version chapter reading. The private repo accepts `versions` on the
chapter route and `passage` already covers comparison, so it would be a second
way to do one thing on the first day of a public contract.

No content negotiation. Language is a property of the version and the version is
in the path.

**Fixing `to_scheme`.** The defect is real, it is named above, and it belongs on
its own branch against B1. B3 pins it rather than papering over it.

## What the verse does not carry yet, and how it gets carried later

The private response has `heading`, `footnotes`, `verse_label`,
`commentary_count`, `cross_references`, `catechism_references` and
`illustration`. None ship here, for three separate reasons.

`heading` is Ave Maria apparatus and is refused on rights, permanently.
`footnotes` and `verse_label` are empty in every row of the source database, so
there is nothing to publish. The rest is data this repo does not have yet.

A null field promising something that never arrives is worse than an absent one,
so they are absent. Keeping the promise findable is the point of this table,
which lands as acceptance criteria in the epics that will own the data.

| Field | Arrives with | Where the promise is recorded |
|---|---|---|
| `commentary_count`, commentary links | B4 | `docs/epics/B4-commentary-cross-references.md` |
| `cross_references` | B4 | same |
| `catechism_references` | B11 | `docs/epics/B11-catechism-cross-references.md` |
| `footnotes`, `verse_label` | when a source carries them | `LIMITS.md` |
| `heading` | never | `LIMITS.md`, rights |

Adding a field to a response model is backward compatible, so nothing has to be
reserved in advance. What has to survive is the intent, and the epic files are
where a reader looks.

## What the first draft got wrong

Recorded rather than rewritten, because the review is the artifact that makes the
second draft worth more than the first.

**The `numbering` field could not hold the data.** An integer pair over a mapping
that splits, merges and partially covers. The ported solution was one file away
and unread.

**Four Psalms figures did not reproduce.** They were measured at verse 1 of each
psalm and reported as facts about psalms. "Two psalms have no `org` counterpart"
was flatly wrong, and the splits at 9 and 113 were missed entirely.

**Twelve, where the answer is 432.** The Douay `blank_upstream` subset presented
as the size of an error class.

**Four ported behaviours dropped without being named**, `previous` and `next`,
`preview`, the formatted reference, and the whole book shape. The epic says to
match the existing shape unless there is a reason, and record the reason.

**A closed set of reason codes that was not closed**, and three of the table's
own cases had no code at all.

**Present tense for things that do not exist**, `make db` and the build script.

**18 MB**, which is the JSON on disk and not what a process holds.

**Nothing on the incoming numbering scheme**, which is how `Sl 51,1` returns the
wrong psalm with a 200.

## Open questions carried into the plan

**How the 219 authored strings are verified.** A conformance case per string is
the rule and a second table transcribed by the same hand is not a check. The
Latin abbreviation file already holds 165 resolution forms, which is independent
evidence for the Latin set and gives nothing for the English one.

**Connection lifecycle.** Read only, opened `mode=ro`. `sqlite3` connections are
not thread safe by default and uvicorn runs sync handlers in a threadpool, so one
connection per process is the answer that looks fine in tests and fails in
production.

**How the tests get a database.** Building the full corpus on every run costs
seconds on every red green cycle. A session fixture over the real file is faster
and couples the suite to a build step.
